# 规则组织说明

最后校对日期: 2026-07-21

## 目标

这份文档只回答一件事:

- `docs/rules/` 以后应该怎么组织, 才能既稳定, 又方便查

这里不替代具体分链路文档, 只定义目录分层原则.

## 总原则

当前更推荐:

- 以功能维度作为主骨架
- 以接口维度承接具体入口细节

也就是说:

- 接口文档写"入口怎么调"
- 功能文档写"系统真实怎么工作"

## 为什么不建议只按接口维度建文档

如果所有文档都按接口拆, 容易出现 4 个问题:

1. 同一个底层规则在多篇文档里重复
2. 多个接口共享一套能力时, 真相会分散
3. 改一处底层逻辑, 很容易漏改一篇旧文档
4. 后续会出现"接口 A 这么写, 接口 B 那么写, 但代码其实共用一套实现"

当前仓库里已经能看到这类风险, 例如:

- 删除能力横跨 `/brands/attachments/delete`、`/brands/delete` 与内部 `delete_document(...)`
- 检索能力横跨 `/search`、`/brands/facts`、`/categories/facts`
- 回调能力横跨上传、确认、删除、知识库更新

所以:

- 纯接口维度不够稳

## 为什么也不建议只按功能维度建文档

如果完全只按功能拆, 也会有问题:

1. 调用方找不到某个具体接口的字段规则
2. 首响应、异步任务、回调格式这些入口细节会被埋掉
3. 一个功能文档会越来越像"总设计说明", 不利于日常改接口时快速定位

所以:

- 纯功能维度也不够落地

## 当前推荐的 4 层结构

### 1. 接口入口规则

适合承接:

- 请求字段
- 兼容字段
- 入参校验
- 首响应
- 分支条件
- 该接口独有的异步行为

典型文档:

- `brand-read-apis.md`
- `documents-upload.md`
- `brands-upload.md`
- `knowledge-update.md`
- `attachment-preview-confirm.md`

### 2. 功能语义规则

适合承接:

- 跨多个接口共享的底层能力真相
- 存删查改到底落到哪一层
- 能力边界与回退逻辑
- 同一路径下多个入口的统一规则

典型文档:

- `delete-semantics.md`
- `search-rules.md`
- `callbacks.md`
- `background-jobs.md`
- `brand-ai-knowledge-ingestion.md`
- `backfill.md`

### 3. 领域口径规则

适合承接:

- 同一个业务字段在多链路里的含义
- 哪张表 / 哪个 JSON / 哪个产物是真相源
- 回调、搜索、编辑、生成知识库时各看哪层

典型文档:

- `product-rules.md`
- `competitors-field-mapping.md`
- `storage-and-tables.md`

### 4. 运行与排查规则

适合承接:

- 状态码和状态枚举怎么看
- 出错后排查顺序
- 哪些现象最容易误判

典型文档:

- `status-enums.md`
- `error-cases.md`

## 判断一篇新文档应该放哪一层

可以用下面这个简单判断法.

### 优先问第一个问题

这篇文档的标题如果写成"某个接口路径", 会不会更自然?

如果答案是会:

- 优先建接口入口规则

例如:

- `/brands/upload` 请求字段怎么解释
- `/knowledge/update` 顶层 `other_info` 怎么传

### 再问第二个问题

这篇文档里的规则, 是否会被多个接口共享?

如果答案是会:

- 优先建功能语义规则

例如:

- 删除到底删哪层
- 检索到底查哪套数据
- 回调什么时候发

### 再问第三个问题

这篇文档关注的是字段、表、结构的统一含义吗?

如果答案是会:

- 优先建领域口径规则

例如:

- `products` 和 `attachment_products` 的边界
- `competitors` 的多套字段映射

### 最后问第四个问题

这篇文档的主要用途是线上排查吗?

如果答案是会:

- 优先建运行与排查规则

例如:

- 状态枚举
- 高频错误

## 当前建议保留为接口文档的内容

下面这些更适合继续保留为接口维度:

1. `brand-read-apis.md`
2. `documents-upload.md`
3. `brands-upload.md`
4. `knowledge-update.md`
5. `attachment-preview-confirm.md`

原因是它们都强依赖:

- 请求字段
- 首响应
- 分支条件
- 独有入库路径

## 当前建议收敛为功能文档的内容

下面这些更适合以功能维度持续维护:

1. 删除语义
2. 检索口径
3. 回调规则
4. background jobs
5. 回补规则
6. 正式知识库入库规则
7. 接口真相矩阵

原因是这些规则通常:

- 会跨多个接口
- 会跨 service / store / callback / OSS / Milvus
- 比接口路径更稳定

## 当前建议优先新增的文档

如果后面继续补规则, 当前我更建议优先新增下面 3 类:

### 1. 冲突会话生命周期规则

建议内容:

- 会话创建条件
- latest 取值规则
- round_no 递增规则
- resolution 提交边界
- force_reingest 语义

原因:

- 这是一套跨多个接口的共享能力
- 更适合建功能语义文档

### 2. 幂等性 / 重试 / 补偿规则

建议内容:

- 上传重试
- 回调重试
- 删除回调补偿
- background job 重跑

原因:

- 这是运行层面最容易埋雷的一组共享规则

## 文件名建议

当前建议文件名保持 3 个原则:

1. 全小写
2. kebab-case
3. 文件名优先表达"能力"或"入口"

推荐风格:

- 接口入口规则:
  - `brands-upload.md`
  - `knowledge-update.md`
- 功能语义规则:
  - `delete-semantics.md`
  - `search-rules.md`
- 领域口径规则:
  - `product-rules.md`
  - `storage-and-tables.md`
- 运行与排查规则:
  - `status-enums.md`
  - `error-cases.md`

## 迁移建议

当前不建议为了追求目录整洁, 立刻大规模改文件名或挪目录.

更稳的做法是:

1. 先在 [INDEX.md](./INDEX.md) 里把现有文档按层分组
2. 后续新增文档直接按这套层次落位
3. 等链接关系稳定后, 再决定要不要做真正的目录迁移

这样做的好处是:

- 不会一下子打断现有引用
- 审查成本更低
- 可以先验证这套结构是否顺手

## 一句话结论

当前最稳的方式是:

- 用功能维度做主骨架
- 用接口维度承接入口细节
- 用领域口径和运行排查文档补齐共享真相
